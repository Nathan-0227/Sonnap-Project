# 報告用的誠實寫法（2026-09-10 核對，資料截至 09-08）

這份檔案的用途只有一個：**把報告裡容易寫過頭的句子，換成經得起追問的版本。**

每一條都附「不能這樣寫 / 要這樣寫 / 為什麼」，以及重跑得出數字的指令。
⚠️ 數字會隨資料成長而變，**引用前先重跑**，不要照抄這裡的值
（這正是本專案方法論第 2 點「問資料不要問文件」）。

```bash
python garmin/run_pipeline.py     # 重算全部分數
python inspect_tapo_score.py      # 攝影機那幾張表
```

## 1. 樣本：是「跨 3 名配戴者」不是「單一使用者」

> ⚠️ **下面的晚數每次重抓 Garmin 都會變。** 寫進報告前先跑一次：
>
> ```bash
> python -c "import json,collections;r=json.load(open('garmin/data/garmin_sleep_quality_final.json',encoding='utf-8'));print(len(r),r[0]['date'],r[-1]['date'])"
> ```
>
> 下面這組是 **2026-09-03 核對**的數字。

| | |
|---|---|
| ❌ 不能寫 | 「本研究以單一使用者連續 64 晚的實測資料驗證」 |
| ✅ 要寫 | 「本研究蒐集 64 晚穿戴資料（2026-05-29 ~ 09-08）。該手錶期間**經手三名配戴者**，其中可確認為同一人的最長連續區段為 41 晚（2026-05-29 ~ 07-27）」 |

**為什麼**：同一支手錶在 2026-05-28 ~ 08-27 之間換過人戴。把三個人的夜晚當成
一個人的縱貫資料，Tier3（今晚的你 vs 過去的你）與 SRI（作息規律性）
在構念上就不成立——那兩者**都是個人內比較**。

實際切分（`garmin/apply_recovery_modifier.py` 的 `WEARER_SEGMENTS`）：

| 區段 | 期間 | 晚數 | 可信 |
|---|---|---|---|
| `wearer_a` | 2026-05-29 ~ 07-27 | **41** | ✅ 唯一可用的縱貫資料 |
| `unverified` | 2026-07-28 ~ 08-27 | **11** | ❌ 已知多人戴過，訊號分不出是一人還兩人 |
| `wearer_c`（專題負責人本人） | 2026-08-28 ~ 09-08 | **12** | ✅ 真實但**仍未達 14 晚** |

⚠️ 最後一列最容易寫錯，而且**寫錯的方向已經換了一次**：以前是 0 晚
（「本人的夜晚一晚都不在資料裡」），現在是 5 晚。

⚠️ **5 晚撐不起「研究者本人長期配戴」這種說法**，而且
`MIN_BASELINE_NIGHTS = 14`，所以**本人這 5 晚的 Tier3 全部在冷啟動、
沒有產生任何個人化修正值**。誠實的寫法是「研究者本人自 08-28 起配戴，
截至 09-08 共 12 晚，尚未達到個人化基線所需的 14 晚」。

⚠️ **具體後果要寫出來**：那 12 晚**沒有任何一晚有 Tier3 修正值**（實測 0 晚）。
報告不能寫「三層評分全數運作」——對研究者本人而言第三層從來沒有啟動過。

⚠️ 分界不是猜的，是用生理訊號本身找的（使用者不記得交接日期）：對每個候選分界
算「左右中位數差 / MAD」，真正的換人會在多個獨立訊號上同時跳躍。A→B 分界處
靜止心率跳 5.73~6.74、睡眠期間平均心率跳 4.13；前 41 晚內部三個訊號的最大跳躍
都 ≤ 1.03。這個方法本身就是可以寫進報告的一段。

✅ **可以放心寫的**：Tier1/Tier2 的基礎分數是文獻加權、**不依賴個人 baseline**，
所以**每一晚的分數本身仍然成立**，不受換人影響。受影響的只有 Tier3 修正值與 SRI。

## 2. `sleep_efficiency` 不是臨床定義的睡眠效率

| | |
|---|---|
| ❌ 不能寫 | 「平均睡眠效率 92%，高於臨床標準 85%」 |
| ✅ 要寫 | 「睡眠效率（Garmin 定義：分母為『起床 − 入睡』，**不含入睡潛伏期**，因此系統性地高於臨床定義）」 |

**為什麼**：臨床定義的分母是「起床 − **上床**」。Garmin 量不到上床時刻，
分母少了入睡潛伏期那一段，算出來一定偏高。拿它去對照臨床門檻是**在比不同的東西**。

⚠️ 這也是 `clinical_efficiency`（Health Connect 算得出）**只供報告、不計分**的理由：
兩種定義餵進同一組門檻（`EFFICIENCY_GOOD = 85`），用不同裝置的受測者會被
**系統性地差別對待**，而那個差異來自裝置不是來自睡眠。

## 3. `movement_sample_minutes` 不是動作量

| | |
|---|---|
| ❌ 不能寫 | 「翻身次數與睡眠品質呈負相關」 |
| ✅ 要寫 | 「`movement_sample_minutes` 是**取樣分鐘數**（每分鐘一筆），不是動作次數」 |

**為什麼**：99.98% 的相鄰取樣間隔正好 60 秒——它量的是「錶記錄了幾分鐘」。
與睡眠時長 r = **+0.929**（睡越久取樣越多，這是同義反覆），
與 WASO 只有 r = **−0.138**。把它當動作量會得到「動越多睡越好」的荒謬結論。

⚠️ 同一個坑還有 `avg_stress_score`：那是**該日曆日白天**的平均
（11439 筆讀數只有 8.6% 落在睡眠期間），**已不計分**。
睡前壓力要用 `presleep_stress_score`（「上一次起床 → 這一次入睡」整段清醒時段）。

## 4. TAPO 的分貝是假資料

| | |
|---|---|
| ❌ 不能寫 | 「系統整合了環境音量監測」 |
| ✅ 要寫 | 「環境音量欄位目前由 `np.random` 產生，**尚未接真實收音**，不參與任何計分」 |

**為什麼**：這是「README 描述的是路線圖不是現況」那類錯誤——本專案已經
拿它批評過外部專案（NightBloom 宣稱整合多種感測器，`grep` 下去零結果），
自己在同一件事上寫過頭會直接失去立場。

⚠️ `ambient_noise_db` 在 data contract 裡有欄位，但 Garmin 手錶沒有這個數據，
TAPO 那邊也還沒有真的收音。**欄位存在 ≠ 資料存在。**

## 5. 攝影機分數目前不參與計分

| | |
|---|---|
| ❌ 不能寫 | 「整合手錶與攝影機的雙模態評分」 |
| ✅ 要寫 | 「攝影機資料目前只用於提供手錶量不到的『上床時刻』；其分數欄位標記為 PROVISIONAL，不進入最終分數」 |

**為什麼**：TAPO 的四代公式（`2.0/0.1/0.4`、`10/5/2`、`95/85/70/50/30`）
**沒有一個數字說得出出處**，而本專案每一項計分都有引文——這是它最難複製的資產，
為了讓架構圖好看而破例，等於把那個資產丟掉（設計紅線 2）。

`itegration/if_integrate.py` 的 `0.6×garmin + 0.4×tapo` **權重無依據**，
輸出已標成 PROVISIONAL。要讓攝影機參與計分，得先寫
`Research-Background/攝影機分數.md`（格式比照 `Garmin手錶分數.md`）。

⚠️ 更根本的問題：同一晚跨來源差 80 分，因為那個分數量的是 **timeline 長度不是睡眠**，
而 timeline 長度取決於**當晚的偵測門檻**，門檻逐晚變過至少四組且沒記在任何欄位裡
→ **跨夜比較在原理上不成立**，不是調係數能修的。細節見 `TAPO_HANDOFF.md`。

## 6. SRI 照算照輸出，但不計分

| | |
|---|---|
| ❌ 不能寫 | 「睡眠規律性指數納入評分」 |
| ✅ 要寫 | 「SRI 計算並呈現，但**刻意不計入分數**」 |

**為什麼**：Czeisler 2026 證實不同計算方法算出的 SRI 差異大到不能對照外部常模。

⚠️ 但**拿 SRI（或 `lights_out_at` 的收斂程度）當挑戰目標不違反這個決定**——
那是個人內比較，不受該問題影響。兩件事不要混為一談。

## 7. 挑戰門檻是 n=1 校準的暫定值

| | |
|---|---|
| ❌ 不能寫 | 「挑戰難度經實證校準」 |
| ✅ 要寫 | 「挑戰門檻以研究者本人的資料（n=1）初步校準，屬**暫定值**，待 D2 收案後重訂」 |

**為什麼**：校準樣本只有一個人，而且那個人特別不規律（平均入睡 02:34、
就寢標準差 84 分鐘）。`作息收斂` 之所以放寬到 ±60 分鐘，是因為 ±30 的達成率是 **0/36**——
那是「這個人的資料撐不起這個門檻」，不是「這個門檻適合所有人」。

⚠️ `target_bedtime` **不能給所有人同一個預設值**：同一批資料
23:30 → 達成率 2%、02:30 → 43%、03:00 → 59%。

## 8. 分數分布本身要一起報

只報平均會蓋掉分布。**2026-09-10 核對的 64 晚**：

| | |
|---|---|
| 分數 | 最低 27.3 / 中位數 84.8 / 最高 100.0 |
| 等級 | Good 42、Normal 15、Poor 5、Bad 2 |
| 有 Tier3 修正值的夜晚 | 28 / 64（其餘因冷啟動或資料無效而停用）。⚠️ **這 28 晚全部落在 `wearer_a` 與 `unverified` 區段**，研究者本人 0 晚 |

⚠️ 同上：重抓資料後這組數字會變，一行指令重算：

```bash
python -c "import json,collections,statistics as st;r=json.load(open('garmin/data/garmin_sleep_quality_final.json',encoding='utf-8'));s=[x['final_score'] for x in r];print(len(s),round(min(s),1),round(st.median(s),1),round(max(s),1));print(collections.Counter(x['final_quality'] for x in r))"
```

⚠️ **Good 佔 42/64 偏高**，報告要主動說明這是**受測者本身睡得不錯**加上
Tier1/2 權重的結果，不要讓讀的人以為系統「只會給高分」。
反面證據是分數確實壓得下去（最低 27.3）且**沒有人為地板**——
這正是設計紅線 3 要守的東西，可以拿來對照外部專案那種「總分被壓在 [50,100]」的做法。

## 9. AI 夢境已補齊，但「生成」不等於「即時」

`ai/data/ai_advice.json` 現在是 **64 / 64 晚，全部由 LLM 生成、0 則規則式退回**
（2026-09-10 補生成 09-02 ~ 09-08 那 7 晚之後）。

| | |
|---|---|
| ❌ 不能寫 | 「系統每晚**即時**為使用者生成專屬夢境日記」 |
| ✅ 要寫 | 「64 晚全數已生成 AI 夢境日記（無規則式退回）。生成為**批次離線執行**，非即時；App 讀取的是已產生的結果」 |

⚠️ 另一件值得寫進報告的是**驗證層真的擋下過東西**：補生成那一輪，09-05
第一次因為「advice 出現了事實區塊裡沒有的數字 30」被拒絕，重試後才通過。
這是「輸出有把關」的具體證據，不是宣稱。

核對指令：

```bash
python -c "import json;e=set(json.load(open('ai/data/ai_advice.json',encoding='utf-8'))['entries']);d={x['date'] for x in json.load(open('garmin/data/garmin_sleep_quality_final.json',encoding='utf-8'))};print(len(d),len(e),'missing:',sorted(d-e))"
```

## 10. 攝影機的整夜有效樣本是 1

錄過 8 個夜晚，但**能拿來分析的完整夜晚只有 1 份**（09-06）。
近四晚：09-06→07 錄 24 分鐘後斷線、09-07→08 無、09-08→09 無、
09-09→10 掛機 233 分鐘只有 17.9 分鐘有資料。

| | |
|---|---|
| ❌ 不能寫 | 「已建置攝影機睡眠監測系統並完成資料收集」 |
| ✅ 要寫 | 「攝影機偵測層已完成校準（三晚人工標註，F1 0.84–0.88），但**整夜連續錄影受限於網路環境**：相機僅支援 WPA/WPA2-PSK，無法加入校園的 WPA2-Enterprise 網路，須依賴手機熱點，而熱點不穩定導致多晚錄影中斷。整夜有效樣本 n=1」 |

⚠️ 這一條是**環境限制不是實作缺陷**，寫清楚反而顯示問題被定位過。
`tapo_netwatch.py` 就是為了分辨「熱點關掉」與「筆電漫遊」而加的。
